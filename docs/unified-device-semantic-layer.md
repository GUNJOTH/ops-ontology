# 统一设备对象与身份映射层

## 目标

本层不把巡检、缺陷、工单和位置明细搬到一张大表中，而是建立一个稳定的业务对象入口，让不同来源的数据通过身份键、位置键和关系表被理解、关联和查询。

## 关系模型

| 关系对象 | 作用 | 数据边界 |
| --- | --- | --- |
| `unified_device` | 统一设备业务对象和最小身份投影 | 只保存设备身份、名称、分类、位置上下文等主数据 |
| `device_identity_map` | 源系统身份映射 | 记录来源系统、源表、源记录号、源键、证据和状态 |
| `business_record_link` | 设备与巡检/缺陷/工单的业务挂接 | 只保存本地挂接关系，不复制业务明细 |
| `function_location` | 位置对象 | 来自只读身份快照，保留位置编码、描述和源位置 ID |
| `location_hierarchy` | 位置父子层级 | 位置层级缺失时保持缺失，不自动推断 |
| `unified_device_relation` | 设备父子或关联关系 | 关系必须带来源、置信度、状态和证据 |
| `device_event` | 业务记录的原始证据索引 | 展示巡检、缺陷、工单的来源记录、描述、位置和挂接状态 |

## 身份规则

1. 设备对象的稳定边界是 `source_schema + SITEID + ASSETNUM`。
2. HD_SAAS 和 XNY_SAAS 默认保持各自系统命名空间，不自动判定为同一设备。
3. 只有存在明确的 ASSETNUM、KKS、业务编号或已确认关系证据时，业务记录才标记为 `accepted`。
4. `needs_review`、`blocked`、`excluded_no_identity_bridge` 只展示证据，不进入已确认设备关系。
5. 源 DM8/MaxiEAM 表不写入；本地关系库和查询 API 不承担正式回写。

## 页面入口

- `/unified-devices`：设备对象、源身份、业务挂接、设备关系和位置上下文。
- `/unified-locations`：位置对象、位置层级、位置下设备和业务记录证据。
- `/metadata`：GRP 元数据语义字典，与设备身份层分开治理。

## 当前边界

当前实现使用本地身份结果快照和 SQLite 关系覆盖层，尚未接入实时 MySQL、Doris 或 EAMi 连接；实时接入应继续沿用只读快照和批次化刷新，不改变页面的语义模型。
