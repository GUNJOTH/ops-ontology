# 统一语义系统页面设计规范

## 设计目标

面向设备语义治理人员和审核人员，优先做到：一眼看清批次质量、快速定位设备、完整看到证据、审核动作可追溯。

整体延续现有 Harness 页面成熟的浅色卡片风格，但增加全局导航、批次上下文、质量漏斗和上下文证据分层。

## 参考设计结论（2026-08-12）

本轮参考 Ant Design、IBM Carbon、Microsoft Fluent 2 和 Material 3 的公开设计规范，提炼为本系统的五条硬规则：

1. **任务优先**：首屏只回答“当前批次到哪一步”和“现在最该做什么”，总览页必须有一个明确的主动作，例如“继续审核 300 条样本”。
2. **筛选与结果同屏**：候选页把搜索、常用筛选、当前筛选条件和结果表放在一个工作区；复杂筛选折叠，不能把用户赶进多层弹窗。
3. **列表到详情渐进展开**：表格只放判断所需的核心字段；KKS、位置、分类、规格、父子关系和规则审计在右侧详情中按区块展开。
4. **批量动作有边界**：选中记录后显示批量操作栏，并明确“已选多少条、动作作用于当前页还是筛选结果”。高风险语义批准默认不做跨证据组批量操作。
5. **审核连续且可恢复**：审核完成后支持“保存并下一条”，保留筛选、列表位置和批次上下文；状态必须同时显示文字和色标，错误必须给出可执行的恢复动作。

这几条规则与当前数据规模直接相关：候选数据约 38 万条，前端只能接收服务端分页结果；审核人员的主要成本是定位证据和连续做判断，而不是浏览装饰性信息。

## 视觉基调

- 页面背景：`#F6F8FB`，减少纯白大面积刺眼感。
- 主面板：`#FFFFFF`，边框 `#E4E8F0`，圆角 12px。
- 主色：`#2563EB`，用于导航选中、主要按钮、链接和焦点状态。
- 辅助蓝：`#EFF6FF`，用于选中行和提示背景。
- 成功：`#15803D` / `#ECFDF3`。
- 警告：`#B45309` / `#FFF7ED`。
- 阻断：`#B42318` / `#FEF3F2`。
- 待处理紫：`#6D28D9` / `#F5F3FF`。
- 正文：`#172033`；辅助文字：`#667085`；分割线：`#E4E8F0`。
- 字体：系统中文字体、微软雅黑；数字可用 `Inter` 或系统无衬线字体。

## 页面骨架

```text
┌─────────────────────────────────────────────────────────────┐
│ 产品标识 / 当前批次                         用户 / 设置      │
├───────────────┬─────────────────────────────────────────────┤
│ 总览           │ 页面标题 + 批次标签 + 只读提示                │
│ 批次管理       ├─────────────────────────────────────────────┤
│ 设备候选       │ 指标卡 / 质量漏斗 / 分布图                    │
│ 审核工作台     ├─────────────────────────────────────────────┤
│ 术语规则       │ 页面主体：表格、列表、详情或审核面板           │
│ 回归测试       │                                             │
│ 正式结果       │                                             │
└───────────────┴─────────────────────────────────────────────┘
```

左侧导航宽度 220px，桌面端固定；移动端折叠成顶部菜单。内容区最大宽度 1440px，页面留白 24px。导航采用任务分组，当前项必须有清晰选中态，不把数据库、规则、审计等实现概念堆成一级入口。

## 页面设计

### 1. 总览页

顶部固定显示当前批次：批次编号、源快照、规则版本、验证器版本、输入数量和只读状态。

第一行指标：

- 处理总量；
- 高质量候选；
- 待审核；
- 已通过；
- 已发布；
- 阻断/异常。

第二行：

- 质量处理漏斗：来源 → 高质量 → 候选 → 待审核 → 已批准 → 已发布；
- 10 个电厂分布；
- 上下文覆盖率：KKS、位置父级、分类、规格、父子关系。

底部显示“需要关注的三件事”，例如：无已确认术语规则、KKS 系统位段目录缺失、位置描述差异记录数。右侧同时给出一个主动作和一个次动作，避免用户读完指标后还要自己寻找入口。

### 2. 批次管理

以表格展示批次：批次号、创建时间、源快照、输入量、候选量、审核量、发布量、规则版本、状态。

批次详情采用时间线：创建 → 质量筛选 → 候选生成 → 校验 → 审核 → 回归 → 发布。

### 3. 设备候选页

采用“筛选栏 + 结果表 + 右侧抽屉”布局，不把 38 万行一次性全部加载到浏览器。默认进入“待审核”视图，搜索框优先支持 ASSETNUM、KKS 和原描述，常用筛选以可移除标签显示。

筛选条件：

- 电厂/站点；
- ASSETNUM；
- 原描述/统一描述关键词；
- KKS/位置编码；
- 分类；
- 候选状态；
- 审核状态；
- 规则版本。

结果表列：设备编码、站点、原描述、统一描述、KKS、位置父级、分类、状态、更新时间。表头固定，核心身份列固定在左侧；证据列允许横向滚动，不在单元格内塞入长段落。

### 4. 设备详情与审核页

右侧或独立页面分成四个信息区：

1. 设备身份：SITEID、ASSETNUM、ASSETID、源快照。
2. 描述对比：原描述、当前候选、待审核修改框。
3. 上下文证据：KKS/位置、父级、分类、规格/特征数量、父子关系、位置状态。
4. 规则审计：命中规则、原因码、规则版本、验证器版本、源行哈希、上下文哈希。

底部动作区固定显示：通过、修改后通过、拒绝、待补证据。修改、拒绝和待补证据必须填写说明。审核完成后主按钮为“保存并下一条”，键盘支持 `Enter` 提交、`Alt + ↓` 下一条、`Esc` 关闭详情；快捷键必须在页面上可见，不依赖记忆。

### 5. 术语规则页

规则表格显示：原词、标准词、规则类型、适用电厂、适用分类、证据来源、状态、版本、影响记录数。

启用规则前显示影响预览：预计改变多少条描述、涉及哪些电厂、是否命中已审核案例。没有回归通过按钮时，启用按钮置灰。

### 6. 回归测试页

显示规则版本、案例总数、通过数、失败数、最后运行时间。失败案例可直接跳转到设备详情和原审核记录。

### 7. 正式结果页

只显示已批准、已发布和发布失败记录。提供发布批次、发布人、审批凭据、发布时间、发布哈希和源快照信息。明确标注“源 MaxiEAM 未回写”。

## 交互原则

- 所有列表服务端分页，默认每页 50 条，最大 200 条。
- 筛选条件保存在 URL，刷新后不丢失。
- 行点击打开右侧抽屉，审核页面保留列表位置。
- 候选页默认展示待审核记录，并提供“当前批次 / 待审核 / 低置信度 / 有上下文差异”四个快捷筛选。
- 选中记录后出现批量操作栏，显示选中数量和作用域；批量动作默认只作用于当前页，跨页操作必须再次确认范围。
- 总览页主动作直接跳到审核工作台，审核页主动作完成当前记录并进入下一条，减少往返导航。
- 抽屉只承担快速查看；需要修改描述、填写说明或查看完整审计时，转为全屏审核页，避免在窄面板内完成复杂表单。
- 批次、规则和发布操作使用二次确认；审核提交支持幂等键。
- 状态用文字 + 色标表示，不只依赖颜色。
- 空状态说明下一步动作；错误提示显示可执行的恢复建议。
- 数据库只读提示在页面标题区长期显示。
- 表格提供紧凑 / 舒适两档密度，加载时间较长时使用骨架屏；分页条固定在结果表底部。
- 页面支持 `Ctrl/⌘ + K` 聚焦全局搜索，所有可操作控件保留清晰的键盘焦点样式。

## 推荐技术实现

- 后端：FastAPI + Pydantic。
- 页面：Jinja2 + HTMX + 少量原生 JavaScript。
- 样式：单独 `static/app.css`，使用 CSS 变量维护主题。
- SQLite：批次、候选、审核、规则、回归和发布写入。
- DuckDB：总览、分布、质量覆盖和频次分析读取。
- API：所有审核和发布操作记录 `audit_event`，不允许前端直接操作数据库。
